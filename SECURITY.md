# Security model and verification

A production deployment must be private and authenticated. Public source visibility does not provide application access control. The Worker supports a trusted authentication proxy, including Sites authentication. Broker routes additionally require the trusted `oai-authenticated-user-id` supplied by Sites dispatch. Do not expose this Worker directly or trust client-supplied identity headers on another host: a self-hosted deployment needs an authenticating proxy that strips/replaces these headers. The local dev adapter only binds loopback and explicitly enables local broker access.

Trading 212 credentials are used by the app server to call fixed HTTPS Trading 212 origins and documented GET endpoints. No order execution, pie modification, arbitrary target URL or redirect following is implemented. Use a key limited to Account data, Portfolio and History–Dividends. Revoke it in Trading 212 if it may have been exposed.

Without Remember connection, credentials remain in page-session memory. With Remember connection, they are encrypted using AES-256-GCM and a fresh nonce per revision in private R2 storage; the key is a separate hosted secret. Ciphertext is bound to the signed-in user through authenticated additional data and a per-user hashed storage path. The server resolves saved credentials; it never returns them to the browser. Neither mode stores plaintext credentials in localStorage, sessionStorage, backups or cookies. Form fields are cleared on submission/navigation. Disconnect and Clear portfolio overwrite the saved connection with a tombstone and remove ciphertext. Conditional object writes prevent older save requests from recreating a forgotten connection. Navigation clears in-memory credentials but intentionally retains an explicitly remembered connection. Disconnect, Clear portfolio and navigation invalidate/abort pending requests; stale results cannot reconnect the session. Authentication failures forget the in-memory session. This prevents accidental persistence, not theft by a compromised browser, extension, origin or hosting provider: the browser and app server must process the credentials to connect.

Broker requests require authenticated dispatch identity, matching Origin, same-origin JSON, bounded streaming bodies (4096 bytes), and HTTPS except explicit loopback development. Requests are throttled per identity in each Worker instance. This is a best-effort instance-local throttle, not a global WAF quota. API responses use no-store/private caching. Security policy restricts scripts/connections to the same origin and permits blob workers needed to decompress larger local Excel files. It blocks external form actions and object embedding. Sensitive upstream errors are not reflected verbatim.

Portfolio records and snapshots are saved unencrypted in browser localStorage. Anyone who can use that browser profile, compromised extensions, or injected same-origin code may read them. Exported JSON backups and original statements are also sensitive files. Clearing the app does not delete downloaded files or attachments from this conversation. Private hosting is access control, not client-side encryption.

Checks cover endpoint guards, stream-size limits, cross-site rejection, session invalidation/abort races, read-only broker methods, redirect restrictions, credential-free error responses and authentication failures. Dependency audit at the time of this change reported no known vulnerabilities. This is a focused code/configuration review, not an independent penetration test or a guarantee of security. Real-account connectivity still requires testing with the user's own read-only credentials.

Remembered credentials are only as private as the signed-in account, application server and encryption-key configuration. Someone controlling the hosting secret can decrypt them. Signing out stops access but does not revoke or delete the remembered API key; use Disconnect / Forget saved connection or revoke the key in Trading 212.
